# ***本阶段的核心问题***

- 系统耗时长，其中主要耗时来自于LLM调用和tavily工具调用，LLM用的是GLM5.3flash，而这个问题我在他们本家的网页试过，他本身就很慢，所以我在考虑要不要换一个LLM，
- 给模型的上下文很长，导致节点超时任务失败，如Synthesizer节点
- 在整个链条的运行中，我没有办法确认哪个节点的输出一定没有幻觉，那么就会导致最终报告如我们所想的每一个事实对应一个证据无法实现
- 工具和LLM调用都是资源，如果在外置节点不断循环验证，必然导致消耗过高
- 我本人并不是全领域的专家，所以甚至我自己都无法验证最终产生的结果，我有想过设计问题数据集制定标准，但是如果这样就意味着我需要先去了解我涉及的问题各方面的内容，才能给出合理的意见和审查，所以这就导致优化工作十分困难。
- 目前的系统并没有记录错误或者未查询的内容

# ***问题解决思路***

- LLM调用慢可能原因：GLM5.3flash默认值是**`max`**，包括"生成一个搜索词"这种根本不需要推理的调用——都在强制跑一轮 `max` 档深度思考
- research_judge的`research_history`会把以前的`ResearchDecision`给加进去，但实际上Decision每一轮都会总结，所以应该传[-1]
- 同一个上下文被反复重发、且没有任何一次命中缓存
- Tavily 用的高级检索search_depth="advanced"，且从来没有真正读取过网页正文，于是形成了三重信息衰减
- 语义校验可以用用 NLI / LLM judge 判断
- 要验证的是"过程可不可审计"
- 对 claim 与 quote 这一对做一次小模型的蕴含判断
- research_plan目前的清单只有‘要解决的问题’+‘下一个问题’，这导致后续节点无法准确定位到‘要解决的问题’的那一个点，整个系统全靠LLM自己输出，无法验证
- research_results和research_judge都把同一个原文读一遍，可以让research_judge写findings，但会导致research_judge任务过重，需要重新拆分research_judge
- research_judge缺的是`跨轮累积的失败计数`,`跨轮累积的证据`,`跨轮累积的清单修正`,这三个能力可以拆到代码里面
