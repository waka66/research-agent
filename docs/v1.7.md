## search_node：节点日志（2026-10-23）

本次只为搜索节点增加观测记录，不改变其他节点和图的停止路由。

- 每次执行在 `finally` 输出一条 JSON 日志，包含 `run_id`、`task_id`、
  `node_name`、`round`、开始时间、耗时、状态、错误及产出摘要。
- `round` 是本次搜索轮次，取状态中已完成轮数加一。
- `output_summary` 记录本轮派发查询数、成功/失败查询数、新增来源数和累计来源数。
  派发查询数不等于已经完成的查询数；取消或处理中断时，摘要可能不完整。
- `query_errors` 记录失败查询及异常类型、信息，不记录完整搜索响应。

| 状态 | 日志级别 | 含义 |
| --- | --- | --- |
| `succeeded` | INFO | 所有查询正常返回；结果为空也算调用成功 |
| `partial_success` | WARNING | 部分查询失败，仍保留成功查询的来源 |
| `failed` | ERROR | 全部查询失败，或节点处理发生未预期异常 |
| `skipped` | INFO | 没有待查询问题，或搜索预算已耗尽，原因写入摘要 |
| `cancelled` | INFO | 节点或内部查询被取消，取消继续向上传播 |

日志状态描述本次搜索结果，不直接控制图的路由：全部查询失败时，沿用原有策略返回
`error_calls`，由后续 `update_node` 判断停止；未预期的处理异常则记录后重新抛出。

当前计数口径保持不变：`search_calls` 累计成功的工具调用，失败另计入 `error_calls`；
没有待查询问题时仍按原逻辑增加一次 `error_calls`。搜索工具可能命中缓存，所以不能
把这些计数解释为实际远程 API 请求数或费用。本次不增加 token、价格或缓存命中字段。

## 第二小块：恢复执行（2026-10-24）

### 一次研究与一次执行

`run_id` 标识研究，也是 LangGraph 的 thread_id，恢复时保留。
`execution_id` 标识一次执行尝试，首次启动和每次恢复都不同。

例如同一个 run_id 可以有三条历史：

| execution | mode | status | 含义 |
| --- | --- | --- | --- |
| E1 | start | failed | 首次执行失败，保留时间和错误 |
| E2 | resume | cancelled | 第一次恢复被取消，独立记录 |
| E3 | resume | completed | 第二次恢复完成 |

后一次恢复不会清空或覆盖前面的记录。状态接口返回最新 execution，检查点仍属于同一研究。
`config.metadata.execution_id` 只用于关联这次尝试的日志；它不替代 thread_id，
也不需要写入业务 state。首次启动和恢复共用 `_run_execution`，差别仅在图输入：
首次传 question，恢复传 None，由检查点决定下一步。

### 恢复入口的顺序

`POST /research/{run_id}/resume` 不需要请求体：

1. 查询 PostgreSQL 研究历史；不存在返回 404。
2. 最新状态只允许 failed、cancelled、interrupted；pending/running/completed 返回 409。
3. 读取检查点，要求存在 checkpoint_id 且 next 非空；缺失或图已结束返回 409。
   检查点暂时读取失败返回 503，不新增 execution。
4. 在短事务内锁定 research_runs 对应行，再检查最新 execution 是否仍是步骤 1 的那条，
   且没有 pending/running 的执行；检查成功才插入新的 mode=resume、status=pending 记录。
5. 提交后重新创建 Queue 和后台 Task，返回 202 与新的 execution_id。
6. 后台使用同一 thread_id 调用 `agent.astream(None, config=...)`。
   新 execution 独立更新 running → completed/failed/cancelled，终态提交后才发送 SSE。

检查点读取不放在研究行锁事务里，避免占用锁等待 I/O。
进入事务后比较 expected_execution_id，可以阻止这种竞态：两个请求都看到 E1 失败，
第一个恢复 E2 很快也结束了，第二个请求拿着过期的 E1 仍想创建 E3。
第二个请求会收到 409，应重新查询状态后再决定是否发起新的恢复。

### 两种锁分别解决什么

- **每个研究的事务行锁 + 部分唯一索引**：行锁串行化同一研究的“检查并创建”；
  `uq_run_executions_active_run` 只对 pending/running 建唯一索引，
  即使绕过应用逻辑，也不能给同一个 run_id 插入两条活跃执行。多个终态历史可以并存。
  锁在事务提交后释放，不覆盖模型调用，也不会阻止不同研究同时执行。
- **服务生命周期的 PostgreSQL advisory lock**：当前 Queue/Task 在单进程内存中，
  服务按单实例运行。独立数据库连接在 lifespan 内持有锁；第二个服务实例启动失败。
  只有获得锁，才将旧 pending/running 标记为 interrupted，填写 finished_at 和
  ProcessInterrupted 错误。这样不会直接根据“当前进程没有 task”去抢另一个实例的研究。

正常关闭服务时，先取消并等待后台任务保存 cancelled，再关闭检查点连接和释放服务锁。
异常退出时连接断开释放锁；下次启动识别遗留记录。interrupted 的 finished_at
是服务发现中断的时间，无法代表旧进程精确退出时间。启动不会自动恢复；用户显式请求恢复。

本次迁移新增索引，没有新增业务字段。迁移若发现一研究有多条活跃记录会明确失败，
需要先核实实际状态，不自动改写历史。当前本地已应用到 `9a24e2d5b130`；其他环境先执行：

```powershell
uv run alembic upgrade head
```

首次升级应先停止旧服务再启动新版本。使用一个应用实例、一个 Uvicorn worker；
多个研究仍可并发，不要使用多个 worker 分担同一个研究服务。

### 手动验收

1. 启动服务，提交一次研究，保存响应中的 run_id 和首次 execution_id。
2. 在已形成检查点后取消，或使用已有的失败研究。查询状态确认 cancelled/failed。
3. 重启服务，再调用下面的恢复接口，确认仍然找到研究，收到新的 execution_id。

   核对最新 mode=resume、执行状态、时间，以及日志里的新 execution_id。
5. 运行中再次恢复应返回 409；已完成研究再次恢复也返回 409。

```sql
ORDER BY created_at, execution_id;
```

在第一个检查点保存之前就失败/取消的研究不能恢复，应新建研究。
如果 execution 失败但图的检查点实际已完成，也会返回 409，不为了改状态再执行已完成的图。
更改了图结构或 state/schema 后，应先验证旧检查点兼容性。

### 验证证据与边界

80 项离线测试通过，覆盖恢复校验、历史不可变、再次恢复、取消、重建队列、
服务锁取得前不得接管、停止任务先于释放锁，以及原有节点/工具逻辑。
9 项真实 PostgreSQL + HTTP/SSE/检查点联调通过，包含以下新增场景：

- 两个恢复请求同时完成检查点校验后争抢数据库，只有一个得到 202，另一个 409。
- 绕过应用行锁直接插入第二条 pending，被唯一索引拒绝；已终态的记录不占用约束。
- 遗留 running 标记 interrupted，终态记录不变；可以创建独立恢复 execution。
- 第二个服务连接无法获得同一把 advisory lock；第一个释放后可以重新获得。
- **真实主图/子图 + PostgreSQL 检查点**：模拟搜索成功后提取超时，关闭原检查点连接，
  清空内存映射，用新连接重新编译图后从 HTTP 恢复。
  主规划、子规划、搜索各调用一次，提取一败一成共两次，最终报告完成；
  最终 research_results 只有一条，旧失败 execution 的所有字段保持不变，
  恢复节点日志关联新的 execution_id。

测试不调用真实模型或搜索供应商；每项数据库测试使用随机的 `test_execution_<uuid>` schema，
历史表和检查点均在其中，结束只删除该测试 schema，避免与正在运行的开发服务互相影响。
联调数据库账号需要创建 schema 的权限。测试表使用 ORM metadata 创建，应用的实际表结构
仍由 Alembic 迁移管理；本地实际表的唯一索引迁移已成功执行。
服务启停顺序使用离线 lifespan 测试，未通过真实杀进程做故障注入。

运行命令沿用上面的常规与 PostgreSQL 联调命令。PostgreSQL 联调文件为
`tests/test_execution_postgres.py`，服务启停测试为 `tests/test_runtime_lifecycle.py`。

恢复以检查点为边界，失败节点内部尚未保存的外部调用可能重做，并不承诺外部请求恰好一次。
事件队列依然只保存当前进程、当前 execution 的实时事件，不回放旧进度；恢复后需要重新订阅。
本块没有增加节点日志持久化、历史列表 API 或运行汇总报告，这些继续按后续小块完成。
当前检查点库可恢复项目的 Pydantic 对象；联调提示未来版本将要求显式注册自定义反序列化类型，
升级相关依赖前需要补齐该配置并回归旧检查点。

## 第三小块：节点与工具记录入库（2026-10-24）

### 保存什么

新增 `execution_records` 表，一次节点/工具调用对应一行，`record_id` 每次重新生成。
通过 execution_id 关联本次启动或恢复，不以节点名、task_id、round 作为唯一标识。
节点重入、循环以及恢复产生不同记录，旧 execution 的过程记录保持原样。

| 字段 | 作用 |
| --- | --- |
| record_id、execution_id | 本次调用和本次执行的身份 |
| parent_record_id | 最近的已保存父调用，如 research_node → search_node → web_search_tool |
| kind、name | node/tool 及名称 |
| task_id、round | 研究任务和轮次，主图节点允许为空 |
| status | running 或结束状态，沿用 succeeded/failed/cancelled/skipped/degraded/partial_success |
| started_at、finished_at、duration_ms | 起止时间与单调时钟测得的耗时 |
| payload JSONB | 完整结构化 record，包含 output_summary、attempts、usage、usage_complete、warnings、error 和工具明细 |

查询与排序字段单独成列，不同节点特有内容留在 payload。节点名/tool_name 等原日志字段仍保留，
不保存完整业务 state、模型提示词或响应正文。纯代码节点不增加 token；未知用量仍为 null。
模型尝试继续存为 attempts 数组，没有单独创建 LLM 调用表。
数据库用复合外键保证父记录属于同一 execution，避免跨执行串联。
`migrations/env.py` 的受管表列表已包含新表。

### 从哪里写入

节点和工具改用 `async with node_log(...)` / `async with tool_log(...)`：

```text
公共上下文入口 → INSERT running，提交短事务
              → 节点原有业务执行，填写 record
公共上下文出口 → UPDATE 同一行的结束状态、时间、payload，提交短事务
              → 输出原有 JSON 日志
```

数据库逻辑集中在 `db/records.py`，公共生命周期在 `graph/observability.py`。
节点只增加 async，不在每个 return 前复制 SQL。Session 只覆盖一次写入，不跨越模型/搜索调用，
并行写入各自创建 Session。running 行首先保存调用身份，业务过程中填写的摘要/工具明细在退出时更新；
没有做逐字段实时更新，也没有把模型 attempts 在执行中单独落盘。

服务的 `_run_execution` 用 `recording_execution(execution_id, record_store)` 开启记录范围。
范围里的 RecordingContext 由异步分支共享，用来汇集 records_complete；
父调用 ID 则用 ContextVar 保存，各异步分支继承父值后分别修改，不会互相覆盖。
这些是执行上下文，不加入业务 state，也不放进 LangGraph checkpoint。
直接独立调用节点/图时，未开启该范围就只输出日志，不自动创建无主数据库记录。

每次写入都会等待结果，内部用受保护的异步任务完成事务；这不是无人等待的后台写队列。
外部取消时先等待正在进行的写入收尾，再传播 CancelledError。
开始写入期间收到取消，不进入业务，开始记录提交后直接保存 cancelled。
业务已经完成、仅在结束写入时收到取消，节点记录保留已完成的状态，外层 execution 仍处理取消。
`model_attempt` 不涉及数据库，继续使用普通 with。

duration_ms 从上下文入口计时，到业务退出、准备结束写入时停止：包含本节点开始入库等待，
不包含自身结束入库等待；父节点仍包含子图和子节点记录开销。模型 attempts 和工具远程请求
另有自身耗时。嵌套与并行节点的耗时不能直接相加为整次执行耗时。

### 入库失败、取消和重启

- 单次记录写入设置 5 秒超时；异常/超时输出持久化错误日志并在节点日志增加 warnings。
  不因记录写入错误覆盖模型/工具的原始异常，也不把业务成功强制改为失败。
- `run_executions.records_complete` 单独表示过程记录完整性。任意分支写入失败都使它变为 false，
  execution 的 completed/failed/cancelled 继续表达业务状态。GET 状态接口返回该字段。
  False 不能通过重复收尾改回 True；它不等于 usage_complete，后者只表示模型用量完整性。
- 父记录开始写入失败时，子记录指向最近已保存祖先（或空），不制造悬空父外键；完整性为 false。
- execution 正常收尾时，在同一事务中检查残留 running，标记 unknown，并使完整性为 false。
  payload 保存 RecordIncomplete 错误和 observed_at。它表示无法确认这条记录的最终状态，
  不把实际业务状态猜成失败或成功。
- 服务取得单实例锁接管遗留 execution 时，同时把其 running 过程记录标为 interrupted，
  保留已结束记录，execution 的完整性为 false。
- unknown/interrupted 只保存发现时间 observed_at；finished_at、duration_ms 保持 null，
  不把重启时刻或当前时间伪装成节点实际结束时刻。

记录失败期间原有日志仍保留；若连 execution 终态也无法提交，继续沿用 persisted=false /
status=unknown 的 SSE 行为。没有增加新的 SSE 进度事件或改变图的业务输出。

### 迁移与手动检查

本地已应用迁移 `3d619a8f2c44`。迁移前的 execution 没有新表记录，
因此 records_complete 初始化为 false，不补造历史；新建 execution 默认 true。
以后恢复会创建新的 execution，新的完整性独立记录，不继承旧执行的不完整标记。
其他环境先停止旧服务、迁移再启动：

```powershell
uv run alembic upgrade head
uv run alembic check
```

提交一次研究，保存 execution_id。在运行中和结束后分别执行：

```sql
SELECT record_id, parent_record_id, kind, name, task_id, round,
       status, started_at, finished_at, duration_ms,
       payload->'output_summary' AS summary,
       payload->'usage' AS usage,
       payload->'attempts' AS attempts,
       payload->'error' AS error
FROM execution_records
WHERE execution_id = '替换成这次的 execution_id'
ORDER BY started_at, record_id;

SELECT execution_id, mode, status, records_complete, error
FROM run_executions
WHERE run_id = '替换成研究的 run_id'
ORDER BY created_at, execution_id;
```

运行中应能看到当前节点为 running；完成后能查看摘要、用量及工具缓存/远程调用信息。
取消后相关记录为 cancelled；失败的父节点和子节点分别保留错误，不把传播链当成多个独立故障。
恢复后使用新的 execution_id 查询，已完成节点不会为了补过程记录而重跑。
